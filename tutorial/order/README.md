# 一笔订单，讲清企业 RAG

入口：http://127.0.0.1:8090/tutorial.html 。原有文档解析、分块、向量实验保留在 `/document-tutorial.html`。

## 开场：为什么需要检索

先问听众：“我的订单 123 现在能退货吗？如果可以，该怎么操作？”

模型参数里没有这笔订单的当前状态。把所有企业资料塞进上下文，也解决不了权限、过期政策、实时事实和来源问题。上下文窗口有限，注意力计算的成本也是原因之一，但不要把“需要检索”简化成“注意力机制记不住”。检索的任务是选出当前用户、当前问题需要且适用的证据。

本教程使用固定教学日期 **2026-10-28**，不会随演讲日期漂移。订单、政策和物流状态全部虚构；H2 SQL、HTTP、Lucene、云端模型和 Milvus 调用真实运行。这里的欧洲政策也只是虚构教学规则，不代表法律。

## 讲述顺序与应用边界

左边按 5 个阶段展示 12 步：**原始文档 → 离线准备 → ① 取业务事实 → ② 筛政策 + 检索条款 → ③ 判断 + 回答**。点任意一步或上一步、下一步，右边先给这一步的关键结果；原始 INPUT / OUTPUT 和 Java 代码默认折叠。先“创建实验”，再逐步运行，或“自动跑完剩余步骤”。尚未运行的节点不填造假的输出。重新运行上游会清除下游结果。

A 是查看政策原文；B 是建立政策检索库，为本次实验做数据准备；C–L 是本次问答链路。A 的 5 份原文供 B 建库；B 的检索库供 F 筛选；D 的订单事实和 E 的签收与售后状态供 K 判断。

| 节点 | 这一步做什么 | 应用 / 端口 | 观察重点 |
|---|---|---|---|
| A 查看政策原文 | 5 份政策文档 → 政策原文 | Spring Boot :8090 · 进程内读取（无模型调用） | 看每份文档的地区、年份、发布状态和原文；政策文本由应用内置，B 写成临时 .md 后解析 |
| B 建立政策检索库 | 政策文本 → 检索库 | Spring Boot :8090 → 智谱 embedding :443 → Milvus :19530 | 解析、分块、向量化并写入 Milvus；本实验通常只需建库一次；关键词索引在 G 临时构建 |
| C 提取订单号 | 问题文本 → 订单号 | Spring Boot :8090 · 进程内正则 | 订单号以问题文本中提取的结果为准；本步骤不做完整意图识别 |
| D 验证归属并查订单 | 订单号 → 订单事实 | Spring Boot :8090 → H2 内存库（JDBC） | 参数化 SQL 同时匹配订单号和演示用户；不属于当前用户就停止 |
| E 查签收与售后状态 | 订单号 → 签收与售后状态 | `Spring Boot :8090 → 本地 mock HTTP 127.0.0.1:<随机端口>` | 查询是否签收、签收日期、是否已有售后申请；URL 由应用生成 |
| F 筛选适用政策 | 订单 + 5 份政策 → 适用政策 | Spring Boot :8090 · 进程内规则 | 按地区、品类、发布状态和购买日期筛选；购买日期选版本，签收日期算期限 |
| G 关键词检索 | 适用政策 + 问题 → 关键词候选 | Spring Boot :8090 · Lucene（按次临时建索引） | 先限定适用政策，再运行 BM25；候选片段还不是答案 |
| H 向量检索 | 适用政策 + 问题 → 语义候选 | Spring Boot :8090 → 智谱 embedding :443 → Milvus :19530 | 即使其他政策更相似，也不纳入候选；Milvus filter 在 Top-K 之前执行 |
| I 合并两路候选（RRF） | 两路候选 → 合并候选 | Spring Boot :8090 · 进程内 RRF | 同一片段去重，按名次计算融合分数，不直接相加原始分数 |
| J 按相关性重排 | 候选 → 相关性排序 | Spring Boot :8090 → 智谱 rerank :443 | 分数反映相关性，不代表政策适用性或答案正确率 |
| K 规则判断与准备模型输入 | 事实 + 证据 → 规则判断 + 模型输入 | Spring Boot :8090 · 进程内规则 + 模型输入组装 | 规则判断由应用代码执行；期限来自结构化字段 returnDays；商品完好等仍待确认 |
| L 生成带引用的回答 | 模型输入 → 回答 + 引用 | Spring Boot :8090 → DeepSeek :443 | 引用编号检查只验证编号对应本轮证据，不验证内容是否支持每句话 |

A 的生效区间包含起始日期，不包含结束日期。

G/H 在实际服务中可以并行。本教程为了观察每个对象，顺序执行。D/E 是事实查询；F 是限定范围；G/H 是找相关条款；I/J 是两种不同的排序步骤。BM25、余弦相似度、RRF、重排原始分数不能直接互相比较，也不是正确率。

G–J 使用片段 A/B 等稳定标识；片段身份、检索名次和引用编号分开显示。G/H 的实际命中片段如果从原文句中开始，页面会标注，并提供“仅供阅读、未发送给模型”的原文上下文。

默认订单 123 应得到：中国区普通商品、签收 3 天、未申请售后；只有 2026 版政策适用，退货申请期限为 7 天，可以有条件申请。商品完好与其他条件未核实，因此不能保证审核通过。

## 每一步的 Java 小实验

源码在 `java-chatbot/src/main/java/chatbot/chat/rag/tutorial/order/`。页面显示构建时直接打包的源文件片段，`demo:start` / `demo:end` 标记对应实际执行方法。查看完整类可以追踪 DTO、注入的依赖及异常处理。

- `OrderData.java`：输入输出 record 契约。
- `DemoOrderRepository.java`：真实 JDBC/H2 查询，不让 LLM 任意拼接 SQL。
- `DemoFulfillmentClient.java`：真实 HTTP 边界；企业落地时替换成经过鉴权的业务 API。
- `OrderPolicies.java`：5 份政策原文（含文档类型）、适用版本筛选和应用规则；版本选择是业务规则，本例使用购买日期，不是永远选最新。
- `OrderTutorialService.java`：解析、分块、向量化、双路检索、合并、重排、模型输入、回答及会话隔离。
- `OrderMilvusIndex.java`（相对 rag 包）：Milvus 的 documentId 过滤请求。

命令行可指定任意终点，自动执行依赖节点，并逐步保存输入输出和 Java 到 `.runtime/order-demo/<runId>/`：

```powershell
# 完整链路
.\scripts\Invoke-OrderTutorial.ps1 -OrderId 123
# 只演示到 SQL / 元数据 / 重排
.\scripts\Invoke-OrderTutorial.ps1 -OrderId 123 -Through sql
.\scripts\Invoke-OrderTutorial.ps1 -OrderId 129 -Through filter
.\scripts\Invoke-OrderTutorial.ps1 -OrderId 123 -Through rerank
```

REST：`POST /api/v1/tutorial/orders/runs` 创建实验（body 为 question）；保留响应的会话 cookie，然后逐步 `POST /runs/{runId}/{node}`。`GET /runs/{runId}` 返回已完成的 traces；`GET /code/{node}` 返回实际源码；`DELETE /runs/{runId}` 清理。CLI 会在 finally 清理自己的教学索引，保存的数据包仍保留。不会删除正式知识库。

## 距离生产的边界

这是可运行的教学链路，保留现有知识库和 NX 功能。固定用户不是企业身份认证；政策 catalog 不是正式的政策发布系统。生产需接入 SSO、租户/资源授权、受治理的政策版本与生效规则、只读业务账号、超时重试与审计、增量索引/删除同步、答案评估。引用编号校验只检查编号范围，不能证明每句事实正确。页面独立展示业务规则结果以便核对；语言模型仍可能误述，需要进一步做逐句证据校验。

SQL/API 可以只选一种，也可以同时接入，依据企业系统提供数据的方式决定。此教程不执行退货退款写操作。
